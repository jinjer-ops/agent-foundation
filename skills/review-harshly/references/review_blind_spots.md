# レビュー観点：過去に自力で気づけなかった欠陥パターン

`/review-harshly` が必ず読み込む観点リスト。**Claude 自身が作ったものを Claude がレビューする際、同じ思考の癖で同じ穴を見逃す**のを防ぐために、実際に外部指摘を受けるまで気づけなかった失敗を汎用チェック項目に変換して置いてある。

各項目の先頭にある `[XXX]` は、その観点が生まれた個別の事例を指す短い符号である。
**事例そのものは非公開の記録にあり、ここには含めない。** 符号は、同じ事例から出た
複数の観点をまとめて見るためだけに残している。

**新しい見落としが判明したら必ずここに追記する。** このファイルが育つほどレビュー精度が上がる。

## 思考パターン（根本原因）

| # | パターン | 具体的な現れ方 |
|---|---|---|
| **P1** | 正常系を先に完成させ、**異常系・権限境界・環境差を後回しにする** | 便利な汎用機能を作ってから制限を後付けする。エラー処理が「投げるだけ」 |
| **P2** | **一般化を急ぐ** | 1つの教訓を、要件が反転する隣接ケースにまで適用する |
| **P3** | **実環境で検証せず「論理的に動くはず」で進める** | 検証手段が手元にあっても使わない |
| **P4** | **自分の過去の出力・自分が定めた手順を疑わない** | 欠損を見たとき、自分の処理より先に外部データを疑う。自分で決めた手順を自分が守らない |
| **P5** | **誰がそれを読むのかを想定しない** | エラーメッセージ・ドキュメントが、書いた本人にしか通じない |
| **P6** | **自分が定めたルールを、自分の作業には適用しない** | [SFU] 「.ps1 は BOM 必須」と本ファイルに書いた**その同じ日**に、BOM 無しの .ps1 を作り、レビューでも気づかなかった。ルールを書くことと守ることは別の作業 |
| **P7** | **意図・予定を「実装済みの事実」として書く** | [SFU] 「エラーなし」「自動再試行がある」「コミット履歴を参照」「GCSに明細が残る」——いずれも実物を確認せずに書き、実態と食い違っていた |
| **P8** | **設計した経路が実際に動いているかを確認しない** | [SFU] 「差分モード」が一度も動作せず全件モードに劣化したまま、13/18 のログに警告が出ていたのに気づかなかった |
| **P9** | **1つのデータ構造を2つの意味で使い、片方の都合で書き換える** | [OWN] 「配分先の候補プール」を絞るために `usersById` を破壊的に縮小したら、同じ Map を参照していた「対象範囲の判定」が反転し、守るはずの担当を全員巻き込んだ。**絞り込みが判定を汚染する** |
| **P10** | **自分が仕掛けた自動化を、自分が忘れる** | [OWN] 「指定日が来たら1回だけ実行して自己削除する」スクリプトを Windows スタートアップに登録したが、失敗し続けたため70日間毎ログオン本番へ破壊的デプロイを試行し続けていた。**失敗時のフォールバックが「次回また実行」だと、無限リトライが常態化する** |
| **P12** | **是正案の前半だけを実装し、後半の欠落が新しい障害を生む** | [NEN] 「失敗行の ID を正しく取る」＋「再試行では直らない失敗を分類する」の2要素からなる是正案のうち、前半だけを実装して反映した。保護が正しく働き始めた**直後に**、削除済みレコードが15分ごとに再試行される無限ループが発生。**安全装置を直すと、その装置の下流にある分類の欠落が初めて表面化する**。是正案は要素ごとに検証方法を書き、反映記録に要素ごとの確認結果を残す |
| **P11** | **手元で動かしたものを、その実行環境で動いた証拠として扱う** | [INS] 全件同期を開発端末（メモリ制約なし）で実行して成功し、同じコードを 512MiB の Cloud Run Job として登録して「反映済み」と記録した。コンテナでの実行回数は0で、必要メモリは上限の2倍以上。**「このコードは動く」と「この実行環境でこのコードは動く」は別の主張**であり、前者から後者は導けない |
| **P13** | **プラットフォームが暗黙に与えていた保証を、移行時に数え忘れる** | [JOB] 取得の二重実行を防いでいたのは Cloud Run service の `--concurrency 1` / `--max-instances 1` だけだった。Cloud Run Job は同じジョブの実行を何本でも並べられるため、移行した瞬間にこの保証が**黙って消える**（エラーも警告も出ない）。自前の実装ではなく設定1つが安全装置になっている箇所は、コードを読んでも見つからない。**移行前に「この構成が無料で与えていた性質」を列挙する** |
| **P15** | **教訓を記録したことで、対処したつもりになる** | [USR] 「制限付き選択リストはエラー駆動で潰すと往復する。値の全体集合と現在値を先に突合する」という教訓を記憶に持っていたのに、**仕組みには入れていなかった**ため、同じ往復が再発した（2026-08-03 に7値で発生 → 2026-09-01 に2値で再発）。記録は再発を防がない。**教訓は、次に同じ場面へ来る人（自分を含む）が読む場所ではなく、通る場所に置く**——コードのガード、テスト、事前チェックのいずれか |
| **P16** | **「いま自分が直したばかりの欠陥」を、直した直後に自分で作る** | [USR] 誤通知（設計上は通知しないはずの経路が通知していた）を直した同じセッションで、新しく足した事前チェックを ERROR で出したため、既存のエラー用メトリクス（本文の "ERROR" に一致）に拾われ、ドライランでもアラートが鳴り、しかも専用メールと二重通知になっていた。**ログの深刻度を1段上げる変更は、既存の通知条件に対する変更でもある。** 足す前に「この文字列を拾っている監視は無いか」を見る |
| **P14** | **保存できたことを、動くことの証拠として扱う（設定・宣言物の場合）** | [JOB] Cloud Monitoring のアラート条件は、保存時と評価時で検証が別。`resource.type` の制約が無い filter は保存で拒否されるが、**保存を通った条件が対象の時系列を1本も持たないことはある**。とくに `conditionAbsent`（デッドマン）は「あるはずの系列が沈黙した」で発火するため、系列が最初から無ければ**何も検知しないまま静かに無効になる**。[DMP] の「2xx を動作したと読む」と同じ形が、コードではなく設定で現れる |

## チェック項目

### A. 実行環境の差（P3・P2・P6 由来 / 実績: F1 Critical, F4, [SFU]）

- [ ] **文字エンコーディング**: BOM の要否を**ファイル種別ごとに**確認したか。`.ps1` は BOM 必須（無いと日本語環境の PowerShell 5.1 が CP932 と誤認して構文エラー）、`.json` は BOM があるとパース失敗。**同じ「エンコーディング」カテゴリ内で要件が反転する**
  - [ ] **[SFU] この変更で追加・変更した .ps1 のバイト列を実際に確認したか**（この項目を読んだ直後に再発させた実績がある。「知っている」と「確認した」は別）
- [ ] **シェルの版**: Windows 標準は PowerShell 5.1（pwsh 7 ではない）。5.1 で動くか
- [ ] **[SFU] PowerShell の引数展開**: `--flag=$hash.prop` は**メンバーアクセスされず** `System.Collections.Hashtable.prop` になる（5.1/7 共通）。`$hash.prop` 単独引数は正しく展開されるため非対称で気づきにくい。`$($hash.prop)` と書く
- [ ] **[SFU] ネイティブコマンドの失敗を握り潰していないか**: `2>&1 | Out-Null` + 無条件の成功メッセージ表示は、失敗を「成功」と表示する。`$LASTEXITCODE` を必ず見る
- [ ] **ロケール**: ja-JP / CP932 環境で壊れないか
- [ ] **改行コード**: CRLF/LF がツールチェーンで変換されて壊れないか
- [ ] **実行ファイルの解決**: `python` が Microsoft Store のエイリアススタブを指していないか（存在確認ではなく `python -c` の**実行結果**で検証する）
- [ ] **[JOB] ファイルを書き換えるスクリプトが、失敗時に元ファイルを消していないか**。`open(path, "w")` は**引数エラーで例外を投げる前にファイルを切り詰める**。実例: `newline` に不正な値を渡して `ValueError` になり、97KB のソースが0バイトになった（バックアップがあったので復旧できた）。**一時ファイルへ書いて `os.replace` する**。書き換え前にバックアップを取る手順は、この種の事故の唯一の保険である
- [ ] **[JOB] 自動生成した編集スクリプトの結果を、目で読んだか**。ヒアドキュメント経由で渡した Python のパッチが**バックスラッシュの行継続を黙って落とし**、複数行のコマンドが1行に潰れていた。**それでも `bash -n` は通り、dry-run の出力も正しく見えた**（意味は同じで、可読性だけが壊れる）。構文チェックとdry-runは「壊れていない」の証明にならない。編集した範囲を読み直す。パターン一致が0件になる失敗が続くときは、ツールチェーンが文字を落としていることを疑う
- [ ] **[JOB] Windows で外部コマンドを `subprocess` から呼ぶとき**: `gcloud` は `.cmd` なので `["gcloud", ...]` は `FileNotFoundError` になる。`shell=True` か絶対パスを使う
- [ ] **配布物を実行環境で実際に動かしたか**。「開発機で動いた」は検証ではない
- [ ] **[OWN] 開発端末に「いつか発火する自動化」を残していないか**。Windows スタートアップ（`%APPDATA%\...\Programs\Startup`）・タスクスケジューラ・cron に、**本番へ書き込む処理**を仕掛けていないか。日付ゲート付きの一回限りスクリプトは、失敗すると毎回リトライして常態化する。仕掛けたらその場で `~/.claude/work/PROJECTS.md` か BACKUP_LOG に「いつ・何を・どこに仕掛けたか」を記録する
- [ ] **[OWN] プラットフォームの実行文脈を取り違えていないか**。「バッチだから非同期枠」は誤り——**コンストラクタは呼び出し側（画面＝同期）の枠で走る**。重い初期化をコンストラクタに置くと、非同期のつもりで同期上限に当たる
- [ ] **[INS] その実行環境で1回でも実行したか**。手元で動いた成果（件数・成功ログ）を、コンテナやサーバレスでの動作証拠として記録していないか。**実行回数を機械的に確認する**（`gcloud run jobs executions list` が空なら未実行）。特にメモリ・実行時間・一時ディスクの上限は手元に存在しないため、手元の成功は上限超過を一切検出しない
- [ ] **[INS] 全件を常駐させる実装になっていないか**。対象件数に比例してメモリが増える構造（全件を list/dict に蓄積、`sorted()` の中間リスト）は、**上限を上げても母数の増加で再発する**。件数で外挿して上限と比べる。集合演算や差分計算は、データを持つ側（DB）へ寄せれば常駐量が件数から独立する

### B. 権限境界と外部入力（P1 由来 / 実績: F2 High, F3, [SFU] Critical）

- [ ] **[SFU] 保存する認証情報の「実効スコープ」を確認したか**。OAuth の refresh_token は**認可時に付与された全スコープ**を保持し、コード側の `scopes=` 引数はそれを縮小しない。`gcloud auth login` 由来の資格情報は `cloud-platform` を含み、所有者が owner なら**その Secret は実質プロジェクトオーナー権限**。tokeninfo で実測すること
- [ ] **[SFU] その認証情報を読める主体を数えたか**。シークレット単位に IAM を絞っても、そのSAを `actAs` できる `roles/editor` 保持者が多数いれば境界にならない
- [ ] **LLM や自動処理が読むデータは攻撃者が書き込める**前提で設計したか（ダッシュボードの説明欄、スプレッドシートのセル、レコードのメモ欄など）
- [ ] **[SFU] LLM の出力を検証せずに書き込んでいないか**。入力トークンとの一致照合、許可値リストとの突合を経ているか
- [ ] **認証情報の送信先が固定されているか**。絶対URLを引数や環境変数で受けると、トークンを任意の外部ホストへ送れる
- [ ] **[AUT] 恒久的に許可しようとしている操作形状を、既に許可済みの操作との「組み合わせ」で評価したか**。単体では無害に見えても合成すると境界を越える。実例: `git push` が許可済みの環境で `git remote set-url` を許可すると「任意の宛先へリポジトリを送出できる」が成立する。**単発の利便性（10秒）と恒久的な境界の引き下げを同じ天秤に載せない**
- [ ] **[AUT] ガードが「自分の設定ファイルの改変」を拒否したとき、別ツールで回避していないか**。設定を書き換えられるなら、その境界は境界でなくなる。回避せず人に判断を返す
- [ ] **破壊的操作の分類**: read / create / update / delete / admin を分類し、それぞれに確認・ロールバック・監査を**設計時に**定義したか
- [ ] **秘密の在り処**: 値がコード・設定ファイル・ログ・チャットに出ていないか。正本は Secret Manager / 環境変数 / 認証ストアか
- [ ] **[SFU] 秘密がローカルディスクに残っていないか**。`.gitignore` は誤コミットを防ぐだけで、端末上の平文は守らない
- [ ] **個人情報**: 氏名・メールアドレス・組織情報が成果物やリポジトリに混入していないか
  - [ ] **[SFU] クラウド側の保存先にも同じ判断を適用したか**。ローカル `output/` を PII として除外しながら、同じ内容を Cloud Logging / GCS に無期限で置いていないか。閲覧できる人数を数えたか
- [ ] **[OWN] 監査ログ/証跡そのものの書き込み保護を設計したか**。読み取り側だけ絞っても、**オブジェクトの共有設定(OWD)が Public Read/Write なら改ざん・削除できる**。ロールバックの唯一の材料が守られていないのは、ロールバック手段が無いのと同じ
- [ ] **[OWN] 「たった1項目の編集権」が、実質どこまでの権限か評価したか**。その項目が自動処理の**入力**なら、書き込み権は「その自動処理が何をするか決める権限」と等価。[OWN] では担当者のテリトリー4項目を書ける＝198万件の所有権を動かせる、だった
- [ ] **[OWN] 画面が制約していることを、サーバも制約しているか**。`@AuraEnabled` / API エンドポイントは UI を経由せず任意の引数で直接呼べる。**UI のバリデーションは検証ではない**

### C. 運用と異常系（P5 由来 / 実績: F5, [SFU]）

- [ ] **エラーメッセージが次の行動を示しているか**。`401 Unauthorized` だけでは利用者は動けない
- [ ] **失敗が検知されるか**。誰にも通知されず、ログを見に行かないと気づけない設計になっていないか
  - [ ] **[SFU] 通知処理が「設定不足で黙って return」していないか**。通知先だけ設定されていると「通知は生きている」と誤読される。無効なら起動時にログへ明示する
- [ ] **[SFU] ドキュメントに書いた確認コマンドを実際に実行したか**。`gcloud logging read` の既定 `--freshness=1d` は、月2回しか動かないジョブでは**常に空を返す**。実行頻度と既定値が噛み合っているか
- [ ] **[SFU] 「正常終了」と「そもそも動かなかった」を区別できるか**。変更0件のとき成果物が何も残らないなら区別不能。毎回必ず証跡が残る設計か
- [ ] **[SFU] ロールバック用の before-image を保存しているか**。変更後の値だけ記録しても元に戻せない。スナップショットは自動か、手動か、どこにあるか
- [ ] **再実行の副作用**: リトライすると状態が変わる操作はないか
- [ ] **失敗モード表**: 何が壊れるか / 利用者が取れる安全な次の一手 / 再試行の副作用、を書き出したか
- [ ] **誰がいつ実行するのか**が決まっているか。「必要になったら誰かがやる」は運用ではない
- [ ] **[SFU] 安全既定がコンテナ化・自動化の過程で反転していないか**。スクリプト単体はドライラン既定でも、`CMD` に `--apply` を書けば「引数を省くと本番が変わる」になる
- [ ] **[JOB] 監視条件が「実際に評価できる」ことを確かめたか**。保存できた＝動く、ではない。**デプロイ済みの条件を読み戻し、その filter と aggregation で時系列を引いて点が返るかを見る。** とくにデッドマン（`conditionAbsent`）は対象の系列が存在しなければ**何も検知しないまま静かに無効**になる。実例: Cloud Monitoring は**監視対象リソースの種類をまたいで時系列を1本に畳めない**（`groupByFields` を空にしても、`project_id` で畳んでも2本のまま）。旧経路と新経路の両方を1つのデッドマンで見る条件は書けず、書こうとすると停止した側が沈黙して必ず誤検知する
- [ ] **[JOB] 監視の対象が、切り替え可能な構成の「片側」に固定されていないか**。退避経路（フォールバック）を持つ設計では、経路を切り替えたときに監視も一緒に移らないと、**退避した瞬間から誰も見ていない状態**になる。切り替えを1つのコマンド／変数に束ね、監視条件もその中で決める。手順書に「アラートも直す」と書くだけでは、切り戻す人が忘れる
- [ ] **[USR] 入力の「新しさ」を、日付の距離で判定していないか**。入力に書かれた日付は**基準日であって届いた日ではない**。「今日から N 日以内」で判定すると、投入が N 日遅れた瞬間に**リトライ窓の全回が同じ理由で弾かれる**（実測: 8/15 基準のシートが 8/17〜18 に投入され、5日間の再試行すべてが「3日前・4日前だから古い」で待機し、その月の人事異動が一度も反映されなかった）。**「前回処理したものより新しいか」で判定する。** 前回処理した識別子を保存し、進んだときだけ処理する。日付の距離は上限のガード（未来日・極端に古い）としてだけ使う
- [ ] **[USR] 終了コードを 0 以外にしたとき、それが「エラー通知」に化けないか**。「異常ではないので通知しない」とコード上で決めても、終了コードが 0 以外ならプラットフォームが**実行失敗として監査ログを severity=ERROR で出す**。エラー用メトリクスが `severity>=ERROR` を含んでいればそれを拾い、アプリが ERROR を1行も出していなくても通知が飛ぶ（Cloud Run Job で実測）。**「待ち」は正常終了にし、待ちが長引いたことは専用の信号で検知する**
  - [ ] ただし、正常終了にすると**デッドマンにも掛からなくなる**。「入力がまだ来ない（待つ）」と「入力の約束が壊れた（人が直す）」を分け、後者は通知側へ倒す。分けないと、書式が変わった瞬間から**永久に無音**になる
- [ ] **[USR] 一斉変更を止めるガードが、影響が最も広い階層を見ているか**。「同じ移動を大勢が同時にした＝異動ではなく改称」を検知する装置が、部だけを見て**本部を見ていなかった**（実測: 29名の本部名が一斉に書き換わる状態を素通りさせた）。**階層構造を持つ属性は、上位ほどブラスト半径が大きい。上位を見ていない一斉変更ガードは、ガードとして成立しない**

- [ ] **[AUT] ガードにブロックされたとき、検討の順序を守っているか**。①その操作が要らない設計はないか ②人が1回叩く ③設定を緩める。**③を先に検討していたら赤信号**。ブロックは設計が過大であることの兆候であることが多い
- [ ] **[JOB] マジックナンバーが「処理の都合」か「入れ物の都合」かを区別したか**。実行時間の上限・バッチ件数・タイムアウトが、業務要件ではなく**プラットフォームの制約に合わせるための値**になっていないか。そういう値は他の判断へ伝染する（実例: 850秒という打ち切りは HTTP の締切 900 秒に収めるための値で、そのせいで別ジョブが同時実行ガードに弾かれ、その回避として処理を1つのループへ畳み込む判断が生まれていた）。**値の由来をコメントに書く。** 「なぜこの数字か」が書けないなら、入れ物の都合である可能性が高い
- [ ] **[KR] 「無いこと」を確かめる陰性テストを、実装したあとに見に行ったか**。陰性の問題は**実装すると期待値が反転する**（「Upgrade ARR は目録に無い」が正解だったテストが、実装した瞬間に不正解になった）。さらに陰性の件数に下限を課している検証があると、1 件移すだけで検証全体が落ちる。**回避（--no-verify）せず、実測して本当に無いものを足す**
- [ ] **[JOB] 移行の目的が「速くする」と「壊れ方を減らす」のどちらかを明言したか**。混ぜると、効果が出なかったときに「やる意味がなかった」と誤読される（実例: 実行基盤の移行でスループットはほぼ横ばい。得たのは 900 秒の崖と衝突による取りこぼしの消滅だった）。**スループットが変わらないことを先に見積もって書いておく**

### G. フォールバックの向き（[SFU] 由来・新設）

判定不能・前提崩れのときに、**危険側に倒れる**フォールバックを書いていないか。

- [ ] **判定不能 → 通過（fail-open）になっていないか**。鮮度チェックが「日付として解釈できないから通す」になっていると、書式が変わった瞬間に安全装置が恒久的に無効化される。**ガードは「不明なら止める」が正しい向き**
- [ ] **絞り込み失敗 → 全件処理になっていないか**。「前回データが見つからないので全件を対象にする」は、ブラスト半径を最大にするフォールバック
- [ ] **フォールバックしたことが検知されるか**。WARNING 1行だけで通知もされないなら、劣化状態のまま常態化する
- [ ] **件数の上限ガードがあるか**。「1回の実行で N 件超の変更なら中断」があれば、上記すべての最後の砦になる
- [ ] **安全装置の保護範囲が、危険の源と一致しているか**。[SFU] では「組織項目の一斉変更」を止める装置が、同じ入力から導出される**権限変更は素通り**させていた
- [ ] **[OWN] 入力欄を空にすると安全装置が外れないか**。JS の `parseInt('')` は `NaN`、`NaN || null` も `0 || null` も `null` になる。**上限値の既定を「未指定＝無制限」にしない**。「上限を最も厳しくしよう」として `0` を入れる操作が、最も危険な設定になっていないか
- [ ] **[OWN] 未知の enum 値が「全件」に落ちていないか**。分岐の末尾が `return true` / `default: 全件` だと、**タイプミス1つでブラスト半径が最大になる**。許可値リストで検査して、外れたら例外にする
- [ ] **[OWN] UIラベルが約束していることと、実際のスコープが一致しているか**。「関西以外」を選ぶと絞り込みが消えて全国になる、といった**除外を約束して包含する**実装。コード内コメントで作者が挙動を認識していても、ラベルが違えば利用者は誤操作する
- [ ] **[OWN] 「画面で選んでも効かない」と言う前に、その選択肢が画面に存在するか確認したか**。ロジック側に `selectedX` / `handleX` / `xOptions` が揃っていても、**テンプレートから一度も参照されていない死にコード**であることがある。`grep <handler> *.html` と `git log -S <handler> -- *.html` の2つで決着する。**プロパティ名だけを見て UI にバインドされていると思い込まない**
