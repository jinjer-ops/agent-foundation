# 新しい共有リポジトリを公開する前の点検

初回公開は、履歴に一度入ったものを消せないという点で通常のコミットと違う。**順序を守る。**

## 1. 境界を決める

1. **可視性を決める。** 既定は private。public にするものは、社内限定情報を1件も含まないことを先に確かめる。
   **フォルダ名は公開境界にならない。** 境界はリポジトリ単位で引く。
2. **正本を決める。** このリポジトリだけが決めていい事柄を1文で書けるか確認する。
   書けないなら、既存リポジトリのフォルダで足りる可能性がある。
3. **所有者を決める。** 障害時に止める・戻す判断をする役割を決める。個人名ではなく役割で書く。

## 2. 最低限の中身を用意する

| 必須 | 理由 |
| --- | --- |
| `README.md` | 何のリポジトリか・前提・使い方・出力・制約。初見の読者がここだけで導入できる状態にする |
| `.gitignore` | 秘密・生データ・生成物・キャッシュを最初から遮断する。後から追加しても既に追跡されたものには効かない |
| `docs/` | 設計・運用・引き継ぎの置き場 |
| `docs/HANDOVER.md` | 次の人がそのまま続けられる引き継ぎ |

`.gitignore` は**追跡を始める前に**書く。除外宣言より先に追跡が始まったファイルには効かない。

## 3. 検査する

```bash
python skills/git-publish/scripts/preflight.py --repo <対象リポジトリ> --scope all
```

- **BLOCK をすべて解消してから初回コミットする。** 履歴に入った秘密情報は、作業ツリーの修正では消えない。
- WARN は件数・件数の多い規則・残す理由・残余リスクを記録する。
- 対象が多いと先頭のみが検査される（未検査の件数はレポートに出る）。分割して実行する。

## 4. 公開する

1. リモートを作成する（既定は private）。**権限が無い場所へは作らない。**
   作成先の権限が無ければ、別の所有者や場所を推測せず止める。
2. ブランチを作り、対象パスだけを明示して stage し、1コミットにする。
3. 既定ブランチへ直接 push せず、PR を作る。
4. PR 本文に、変更範囲・実行した検査と結果・未解決の判断・意図的に検証していないことを書く。

## 5. 索引へ登録する

**共有リポジトリを作ったら、索引リポジトリの台帳へ1行追加する。** 登録しないと「どこに何があるか」が
辿れなくなる。台帳の場所と記入項目は索引リポジトリの `CONVENTIONS.md` と README に従う。

各リポジトリの `CLAUDE.md` から共通運用ルールを参照させる。これが横断ルールの適用口になる。

## 6. 公開後に確認する

| 確認 | 方法 |
| --- | --- |
| 初見の読者が導入できるか | 別ディレクトリへ clone し、README だけを見て検証コマンドまで到達できるか試す |
| 秘密が履歴に無いか | 追跡ファイル全体を検査する。混入していた場合は削除ではなく失効・ローテーションが必要 |
| 可視性が意図どおりか | リモートの設定を目で確認する。旧 URL からのリダイレクトは壊れて見えないため注意する |
