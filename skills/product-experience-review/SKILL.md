# 製品体験レビュー

利用者が読む出力が**製品として出せる水準か**を評価する。コードの正しさは見ない
（それは `audit` / `review-harshly`）。ここで見るのは、**読んだ人が分かり、信じられ、
次に何をするか決められるか**である。

「社内ツールだから」は基準を下げる理由にしない。**社外の顧客に提供できるか**を
既定の基準にする。社内でしか通じない語・内部の番号・作り手の都合の並びは、
社内の利用者にとっても同じだけ負担である。

## 0. 評価の契約（最初に書く）

評価を始める前に、次を短く書く。分からない項目は推測で埋めず「未確定」と書く。

1. **対象**: どの出力か（画面・ファイル・通知）と、**利用者が実際に見る形**。
   Markdown や JSON の生の形ではなく、描画された形で評価する。描画された形が
   無ければ、先に**最小のモック**（HTML 1 枚で足りる）を作ってから評価する。
2. **利用者**: 役割、経験年数、読む場面（移動中のスマートフォン、会議の直後、
   週次の 1on1 など）、読む時間の目安。
3. **読んだ後の行動**: 利用者が次に何を決める・何をするか。これが評価の軸になる。
4. **配布範囲**: 社内のみ／社外の顧客にも出す。既定は「社外にも出す」。
5. **制約**: 出してはいけない情報（個人情報・他の顧客の情報・社内の数字）、
   数字の確からしさ（推定の精度・標本の大きさ）。

## 1. 立場ごとに独立して読む

[references/lenses.md](references/lenses.md) の立場から、**立場ごとに別々に**読む。
ほかの立場の結論を見てから読まない。高リスク（社外へ出す、人の評価に使う、
金銭・契約に関わる）なら全立場を別のエージェントで並列に実行する。そうでなければ
「初見の利用者」「日本語の編集者」と、関係する 1〜2 立場で足りる。

各立場は、次の 3 つの問いに答えてから指摘を書く。

- **30 秒で**: 最初の画面だけを見て、何が分かり、何が分からないか。
- **次の一手**: 読み終えた利用者は、次に何をすればよいか分かるか。
- **信頼**: 数字や主張を、利用者が信じてよい理由（根拠・限界）が見えるか。

## 2. 指摘の書き方

1 件ごとに次を揃える。揃わないものは指摘にしない。

| 項目 | 内容 |
| --- | --- |
| 重さ | **S1** 出してはいけない（誤解・不当な評価・情報漏えい・読めない）／**S2** 社外に出す前に直す／**S3** 磨き |
| 場所 | 節・行・要素。**原文を引用する** |
| 問題 | 何が起きるか（利用者の立場で） |
| 理由 | なぜ問題か。一般則への言い換えでなく、この利用者にとっての影響 |
| 書き換え | **そのまま差し替えられる文**。「分かりやすくする」のような方針だけの案は書き換えではない |

言葉の直しは [references/copy_rules_ja.md](references/copy_rules_ja.md) の規則を使う。
内部の語を利用者の語に置き換えた**対訳表**を必ず作る（対象の出力に現れた語だけ）。

## 3. 反証する

指摘ごとに、次を試してから確定する。

1. **本当にこの利用者の問題か。** 想定した利用者・場面で起きるかを確かめる。
   作り手の好みの差は S3 以下にする。
2. **書き換えが正しさを損なわないか。** 分かりやすくするために、不確かさを隠す・
   確率を断定に変える・根拠の無い安心を与える、になっていないか。数字の丸めで
   順位が変わっていないか。
3. **同じ原因の指摘をまとめる。** 「内部 ID が見える」が 5 か所あれば 1 件にする。

## 4. 報告

次の順で書く。

1. **結論**: このまま出せるか（出せない／社内なら可／社外にも可）と、その一番の理由。
2. **指摘**: 重さの順。S1 → S2 → S3。
3. **対訳表**: 内部の語 → 利用者の語（と、必要なら 1 行の説明）。
4. **構成の提案**: 最初の画面に何を置き、何を畳むか（詳細・根拠・技術情報）。
5. **良い点**: 残すべきもの。直す作業で壊さないため。
6. **評価していないこと**: 実際の利用者で試していない、端末の種類、表示速度、
   別の事例（難しい事例・うまくいった事例・情報が欠けた事例）での見え方など。
   **このレビューは利用者での検証の代わりにならない。** 検証すべき仮説として書く。

## 5. よくある欠陥（最初に疑う）

- 内部の番号・版・モデル名・処理の段の名前が、利用者の見る面に出ている。
- 統計の語（百分位・中央値・AUC・オッズ比・確率の小数）を、そのまま利用者に見せている。
- 数字を文章の中で読み上げている（「受注確率が 0.195、百分位 21」）。数字は図や
  ラベルで見せ、文章は意味を言う。
- 注釈番号（[F14] など）が根拠の主な見せ方になっていて、根拠に辿り着けない。
- 足りない点だけを並べ、**できていた点**が無い。コーチングとして受け取れない。
- 評価の対象（本人の腕か、状況の難しさか）が区別されず、責められていると読める。
- 作り手の処理順（層 1 → 層 2 …）で並んでいて、利用者の関心の順（結論 → 次の一手 → 根拠）でない。
- 同じ相手を別の語で呼ぶ（社内／担当者、社外／顧客／お客様）。
- 「読み方」の注意書きで分かりにくさを補っている。注意書きが要る表示は、表示を直す。
- 空の状態・欠けた状態（助言が出なかった、測れなかった）が、利用者に説明されていない。
- 1 回だけを切り出していて、利用者の実際の関心（その案件の流れ全体）に答えていない。

## 6. モックを作るとき

- 利用者が実際に見る媒体（PC の画面・スマートフォン・通知）の幅で作る。
- **本物の顧客データをモックに入れて外部のサービスへ置かない。** 共有するモックは
  合成データで作る。実データのモックは、データを置いてよい場所にだけ置く。
- 1 画面目に置くのは 3 つまで（結論・次の一手・理由の要約）。残りは開いて読む。
- 同じ構成で、性質の違う事例を少なくとも 2 つ流し込む（うまくいった事例と、
  難しい事例）。1 事例だけでは構成の良し悪しが分からない。
